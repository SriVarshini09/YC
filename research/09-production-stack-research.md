# Buy the plumbing, own SHAPI's evidence loop

SHAPI can reach production quality mostly by adopting existing parts and building only the pieces nobody sells. The parts to adopt or buy are oasdiff for structural diffs, tree-sitter/ast-grep plus each language's own type checker for extraction, a Firecracker-class sandbox (E2B or Daytona at about **$0.05 per vCPU-hour**), a GitHub App built on Octokit with Renovate-style noise controls, and Postgres plus a durable job engine (Trigger.dev or Hatchet). SHAPI should build what no vendor sells: a privacy-safe shape sensor, statistical drift detection on JSON fields, an OSV-format advisory database with verified provenance, and a verification-gated repair loop whose fix outcomes, pooled across customers, become a "merge confidence" dataset. That split matters because the money and the risk sit in different places. Compute and LLM costs are trivial: a sandboxed verify run costs about **$0.014** and a Sonnet 5.5 repair attempt about **$0.09**. The real risks are licensing traps, rate limits and trust. **CodeQL and Semgrep's registry rules are legally off-limits** for a SaaS scanning private customer code. GitHub never retries failed webhooks. Bot PRs that are noisy or wrong destroy adoption faster than missing coverage does. The market evidence points the same way. As of October 2026, consumer-side "your API changed" tools are indie, alert-only products at **$10–35/month**, and producer-side tooling is being bought up: Stainless by Anthropic, Fern by Postman, Optic by Atlassian. YC's Fall 2026 "Self-Maintaining APIs" request has no clear incumbent ([YC on X](https://x.com/ycombinator/status/2079963746764808559)). SHAPI wins on fix quality and evidence, not on alerting.

## The recommended stack fits one table: adopt engines, build the judgment layer

The prototype already spans every layer. What it lacks is durability: no multi-language mapping, no real isolation, no app identity, no persistent multi-tenant store. The table below gives the production recommendation for each layer, and the sections after it give the evidence.

| Layer | Prototype today | Production recommendation | Buy / build / adopt |
|---|---|---|---|
| **Sensor** | GitHub and Stripe canaries | A canary fleet on static egress IPs with multi-probe confirmation, plus opt-in in-process shape hooks per runtime (undici/fetch, httpx/requests, Go `RoundTripper`, OkHttp) that emit *shapes, not values*, as OTel attributes. The OTel Collector redaction processor sits behind them as a fail-closed backstop. eBPF only later, as an optional Linux path | Build the hooks; adopt OTel |
| **Contract/diff** | Homegrown inference + diff, SQLite | Keep the inferrer, which tracks value classes and per-field statistics. Project shapes to OpenAPI 3.1 and run **oasdiff** for structural checks. Keep homegrown statistical drift checks. Store in Postgres | Adopt oasdiff (Apache-2.0); build drift |
| **Mapping/extractor** | ts-morph, TS/JS only, intra-file | Tier 0: tree-sitter/ast-grep in every language. Tier 1: type passes (TS compiler/ts-morph, Pyright, go/types, JavaParser). Tier 2: cached SCIP indexes. Joern optional for deep Java/JS/Python flows | Adopt permissive OSS; build the narrow dataflow; **never CodeQL or Semgrep registry rules** |
| **Advisory** | 7 hand-researched advisories | OSV 1.9.2-shaped records under CC-BY-4.0. Deterministic adapters for structured sources, LLM extraction from page diffs with a validator that requires a verbatim source quote, a GHSA-style `reviewed` flag, and Deprecation/Sunset header sightings | Build (this is the moat) |
| **Repair** | One status-code recipe, Claude fallback | ast-grep YAML recipes plus per-language precise fixers. A Messages API tool loop escalating Haiku to Sonnet 5.5 to Opus 5.5, capped at 3–5 turns, with test files locked | Build recipes; buy the model |
| **Verification** | Contract tests for fetch only; temp-dir copy | Per-language HTTP-stub harnesses (nock/msw, respx/responses, httptest/go-vcr, WireMock) in a Firecracker microVM with egress denied by default and a caching registry proxy. "Run in the customer's CI" offered as a tier | Buy the sandbox; build the harness |
| **Delivery** | User token + Git data API; MCP server and skill | A GitHub App on `@octokit/app`/`@octokit/webhooks` (or Probot v14). | **Backend** | Local SQLite | Postgres with row-level security, Trigger.dev or Hatchet, Fly.io or Render, Doppler plus KMS envelope encryption for OAuth tokens, WorkOS for enterprise SSO, and a SOC 2 platform | Buy |

The pattern across rows is consistent. Wherever a component is **commodity and permissively licensed** (diffing, parsing, sandboxes, queues), SHAPI should adopt it. Wherever the work requires **cross-customer judgment** (is this drift real, does this fix work, is this advisory true), SHAPI should own it, because that is where the compounding data asset forms.

## Detection should hook the HTTP client in-process, then diff with oasdiff

The first constraint shapes everything downstream. **OpenTelemetry deliberately does not capture HTTP bodies.** Bodies sit outside the HTTP semantic conventions, and the spec discussion notes the client span usually ends before the body is read ([opentelemetry-specification #1284](https://github.com/open-telemetry/opentelemetry-specification/issues/1284)). The Java agent exposes only body *sizes* as experimental attributes ([OTel Java agent docs](https://opentelemetry.io/docs/zero-code/java/agent/instrumentation/http/)). Node's undici instrumentation does give a `responseHook` and diagnostics-channel lifecycle events to attach to ([instrumentation-undici README](https://unpkg.com/@opentelemetry/instrumentation-undici@0.30.0/README.md)). Plain OTel therefore gives SHAPI status codes, headers and URLs but no field-level shape. The portable answer is a small in-process hook per runtime that computes the shape where the body is visible and emits only the shape: path, JSON type, value class, nullability and array-length bucket. The hook should observe only an allowlist of known provider hosts and sample per endpoint. On the customer side, the OTel Collector's `redactionprocessor` makes a good second layer: it is "designed to fail closed", deletes any attribute not on `allowed_keys`, and can HMAC-hash retained values ([redactionprocessor README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/redactionprocessor/README.md)).

**eBPF should not be the primary path, and Akita's history shows why.** Postman bought Akita in July 2023 for eBPF-based traffic discovery ([BusinessWire](https://www.businesswire.com/news/home/20230719991128/en/Postman-Acquires-Akita-Software-to-Help-Build-the-Future-of-API-Observability)) and sunset the Akita product on 14 March 2025 ([Postman notice](https://www.postman.com/lp/akita-sunsetting/)). Its successor agent is still described as **alpha, focused on ECS**. HTTPS capture is opt-in and Linux-only, needs kernel 5.8+, and requires CAP_BPF plus CAP_PERFMON ([postman-insights-agent](https://github.com/postmanlabs/postman-insights-agent)). Go binaries need uprobes on `crypto/tls` that fail on stripped builds ([Kubeshark docs](https://docs.kubeshark.com/en/encrypted_traffic)). Grafana's Beyla, donated to OpenTelemetry as OBI, emits traces and metrics, not payloads ([Grafana blog](https://grafana.com/blog/2025/05/07/opentelemetry-ebpf-instrumentation-beyla-donation/)). None of this works on Lambda, Cloud Run or Vercel, where many SaaS integrators run. What Akita does give SHAPI is a **citable privacy precedent**: "all data-format inference happens on the client side, before the data is removed" ([Postman Insights security](https://learning.postman.com/latest-v-12/docs/insights/data/repro-mode-security)). That is SHAPI's model, and security reviewers will recognise it.

Shape-only capture still leaks in two places, so the sensor needs two more protections. First, it should collapse map-like objects whose keys look like IDs or emails into a `{<dynamic-key>: shape}` form. Second, it should send enum candidates only as per-customer HMACs with counts, revealing plaintext only for values already in the provider's public docs or seen across enough tenants. It should not hash every field name, because that would destroy the cross-customer comparison that is SHAPI's edge. Postman itself admits keyword and regex redaction is imperfect, and that unrecognised secrets may be stored for up to 30 days ([Postman Insights security](https://learning.postman.com/latest-v-12/docs/insights/data/repro-mode-security)). Treblle-style masks that keep the original length should be avoided, because length is a side channel ([Treblle masking](https://docs.treblle.com/treblle/data-masking/)).

For diffing, SHAPI should **stop maintaining its own structural taxonomy and embed oasdiff**. It is Apache-2.0, embeddable as a Go library, supports OpenAPI 3.0, 3.1 and 3.2, and detects **773 distinct changes** with IDs and ERR/WARN/INFO severities ([oasdiff.com](https://www.oasdiff.com/); [BREAKING-CHANGES.md](https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md)). It already handles subtleties SHAPI would otherwise rediscover: nullability judged by request vs. response direction, `x-extensible-enum` so that added response enum values do not raise hard errors, and deprecation-before-removal. The mechanism is to project each inferred shape onto an OpenAPI response schema per endpoint template and status, then diff. SHAPI's homegrown diff should stay for what specs cannot express: status-code drift, header drift, value-format drift (Google AIP-180's "IPv4 to IPv6" class ([AIP-180](https://google.aip.dev/180))), presence-rate drift and null-rate drift. No direct prior art for statistical drift on third-party API responses turned up. The nearest analog is data observability's null-rate and cardinality monitors ([Monte Carlo](https://montecarlodata.com/blog-how-to-build-your-own-data-anomaly-detectors-using-sql)). SHAPI can treat each (provider, endpoint, status, field path) as a column and apply two-proportion or divergence tests with minimum sample gates. One rule is non-negotiable: a field counts as "removed" only when it is statistically absent where it used to be present, never because one sample lacked it, since quicktype-style merging silently turns missing fields into optional ones ([quicktype blog](https://quicktype.io/blog/quicktype-multiple-samples)). Enum semantics also differ by provider. Stripe distinguishes open from closed enums and may add values to open ones without a version bump ([Stripe enums](https://docs.stripe.com/api/enums)), yet it sometimes tags enum additions as breaking ([Stripe changelog](https://docs.stripe.com/changelog/2024-06-20/adds-enum-disabled-reasons-capabilities)). Severity must therefore be set per provider, not globally.

The canary fleet needs operational hygiene more than new technology. Fly.io's default egress IPs "are unstable and may change". App-scoped static IPv4s cost **$3.60/month per region**, survive deploys, and cap at 64 Machines per IP and 1,024 concurrent connections per destination IP ([Fly egress IPs](https://docs.fly.io/networking/egress-ips)). Render's alternative is $100/month for a set of three ([Render changelog](https://render.com/changelog/add-dedicated-outbound-ips-to-your-workspace)). False-positive control is a design issue, not a vendor choice. Separate transport and auth failures (5xx, timeouts, 401, `invalid_grant`) from 429s and from real shape diffs. Require confirmation across probes and egress IPs, normalise volatile fields, and send infrastructure failures to on-call rather than to the advisory pipeline. Canaries should also log every `Deprecation` (RFC 9745, Standards Track since March 2025) and `Sunset` (RFC 8594) header they see ([RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html); [RFC 8594](https://datatracker.ietf.org/doc/rfc8594)). No evidence of wide provider adoption turned up, so these headers corroborate advisories rather than supplying coverage.

## Licensing, not capability, decides the extractor and codemod stack

Moving from ts-morph's single-language, intra-file analysis to multi-language mapping runs into a hard truth: **no permissively licensed, SaaS-safe engine gives mature cross-file dataflow for TypeScript, Python, Go and Java.** The two strongest engines are both blocked. The CodeQL CLI license prohibits use "in connection with any codebase that is not an Open Source Codebase" and use "as a hosted solution", unless the user holds a paid GitHub Advanced Security license ([codeql-cli-binaries LICENSE](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md)). Semgrep's engine is still LGPL-2.1, but its rules moved to the Semgrep Rules License, which **bars SaaS and competing use** of every Semgrep-authored and community-contributed registry rule ([Semgrep FAQ](https://docs.semgrep.dev/faq/comparisons/opengrep-1)). Cross-file analysis in Semgrep Pro is commercial, runs only on full scans, and drops back to single-file mode past 5 GB of memory or 3 hours ([Semgrep Pro docs](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro)). GitHub's stack-graphs was archived on 9 September 2025 ([archived repo](https://proxy-ga.blitzz.co/proxy/123456/web.archive.org/web/20260601045401/https:/github.com/github/stack-graphs)).

| Trap | What is restricted | Safe alternative |
|---|---|---|
| **CodeQL** | Any non-open-source code; any hosted use without GHAS ([LICENSE](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md)) | Only if the customer runs it under their own GHAS license in their own CI (needs a legal read) |
| **Semgrep registry rules** | SaaS or competing use ([Semgrep FAQ](https://docs.semgrep.dev/faq/comparisons/opengrep-1)) | Opengrep or Semgrep CE (LGPL) run as a subprocess with **SHAPI-authored rules only** |
| **OpenRewrite JS/TS (Moderne MSAL)** | Closed-source repos need a Moderne license ([rewrite-javascript](https://github.com/openrewrite/rewrite-javascript)) | Apache-2.0 OpenRewrite core for Java only; ts-morph for TS |
| **GritQL** | MIT, but acquired by Honeycomb in April 2025 ([Honeycomb](https://www.honeycomb.io/blog/honeycomb-acquires-grit-and-expands-leadership-team-to-accelerate-customer-value-and-enterprise)) | Usable, but not as a core dependency |
| **Provider sandbox / ToS** | Automated probing and republishing changelog prose are not yet legally reviewed | Facts such as dates and endpoints are generally safe; verbatim migration text needs legal review |
| **Data you cache** | Cached indexes count as derived customer code under DPAs | Persist only the call-site index, never source |

The workable architecture is tiered, and it fits SHAPI's narrow need. SHAPI does not need a general taint engine. It needs to know which fields of a response object are read, which statuses and enums are compared, and which headers are sent. **Tier 0** is tree-sitter via ast-grep for syntax-level call-site discovery in every language. It is fast and never fails, but it misses aliased clients and dependency-injected wrappers. **Tier 1** runs real type resolution only on files that contain candidate call sites. Type attribution is what lets a tool tell an Octokit receiver from a lookalike, which is the canonical lesson of OpenRewrite's design ([OpenRewrite LSTs](https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees)). Moderne marketed "first type-attributed JavaScript & TypeScript refactoring" in October 2025, a sign that this is the commercial differentiator ([BusinessWire](https://www.businesswire.com/news/home/20251014739134/en/Moderne-Expands-Modernization-Platform-With-First-Type-Attributed-JavaScript-TypeScript-Refactoring)). Type passes cost about as much as type-checking the repo: scip-typescript ran at roughly **1k–5k lines per second**, bottlenecked by `tsc` ([Sourcegraph](https://sourcegraph.com/blog/announcing-scip-typescript)), though that figure dates from about 2022. **Tier 2** caches SCIP indexes for cross-file references. **Joern** (Apache-2.0) is the only open-source multi-language engine with real interprocedural dataflow. Its docs rate its Java frontend Very High, JavaScript and Python High, and Go only Medium ([Joern docs](https://docs.joern.io/)), so it suits an optional deep pass, not the core path. Type passes require installed dependencies, so they have to run inside the sandbox described below. They must degrade gracefully to Tier 0 when a repo will not build.

For codemods, **ast-grep YAML should become SHAPI's universal recipe format**. Its text-splice rewrites leave untouched code byte-identical. Type-dependent edits go to per-language precise fixers: ts-morph for TS, LibCST for Python (Bowler's own README now points to LibCST ([PyPI bowler](https://pypi.org/p/bowler))), go/ast with gofmt, and JavaParser or OSS OpenRewrite for Java. Codemod.com's open-source CLI already combines ast-grep with multi-step YAML workflows and MCP tools ([codemod/codemod](https://github.com/codemod/codemod)), a useful reference if not a dependency. Moderne's operating model is the one to copy. It builds type-attributed trees once per repo, serialises them, and runs tested recipes against the cached trees in parallel ([OpenRewrite FAQ](https://docs.openrewrite.org/reference/faq)). Its `rewriteTest` framework **deliberately has no option to ignore formatting differences** ([OpenRewrite FAQ](https://docs.openrewrite.org/reference/faq)), so any formatting regression fails the test. SHAPI recipes should ship with before/after fixtures, negative "must not change" fixtures, and an idempotency test that re-running on fixed code yields no diff.

## Verification-gated repair costs cents; isolation is where to spend

SHAPI's contract test is a *consumer-side* test: the customer's code runs against a stub that returns the old shape, then the new one. That rules out the famous tools as the main mechanism. Schemathesis generates property-based tests that target servers ([Schemathesis docs](https://schemathesis.readthedocs.io/en/stable/)). Pact's value rests on providers verifying contracts, which Stripe and GitHub will not do for SHAPI ([Pact spec](https://docs.pact.io/implementation_guides/pact_specification)). The right primitives are in-process HTTP stubs fed by one SHAPI fixture pair (old.json/new.json) per language: nock or msw for Node, respx or `responses` for Python, `httptest` or go-vcr for Go, and WireMock for Java. A spec-driven server is the fallback whenever the SDK base URL is configurable. WireMock's "hard" OpenAPI validation mode also catches requests the new spec would reject ([WireMock docs](https://docs.wiremock.io/openAPI/openapi-validation)). Prism works the same way, but its authors say it "is not yet intended for programmatic mocking within test suites" ([jvt.me Prism guide](https://www.jvt.me/posts/2022/03/04/openapi-local-prism/)). Extending SHAPI's fetch-only test generation to cover the Octokit and Stripe SDK call sites it already extracts is the highest-leverage verification work. Provider sandboxes belong only in an optional "live smoke" step. Stripe can now provision anonymous sandboxes from the CLI for coding agents ([Stripe Sandboxes](https://docs.stripe.com/sandboxes)). QuickBooks sandboxes, by contrast, are capped at 10 companies, last two years and cannot be renewed ([Intuit FAQ](https://developer.intuit.com/app/developer/ies/docs/develop-your-app/sandboxes/sandbox-faqs)).

The prototype's temp-dir copy is the single largest production gap, because SHAPI runs customers' install scripts. **Rootless Docker shares the host kernel; the minimum bar is gVisor, and the right default is a Firecracker microVM.** Firecracker boots in about 125 ms with under 5 MiB of overhead ([Northflank](https://northflank.com/blog/what-is-aws-firecracker)). gVisor intercepts every syscall in a Go user-space kernel but leaves some filesystem and ioctl APIs unimplemented, a compatibility risk for test suites ([gVisor security](https://gvisor.dev/docs/architecture_guide/security/)). Cost should not drive the choice:

| Sandbox option | Rate | ~2 vCPU / 4 GiB per hour | Notes |
|---|---|---|---|
| E2B | $0.000014/vCPU-s + $0.0000045/GiB-s | ~$0.17 | Firecracker per sandbox; Pro $150/mo; BYOC on Enterprise only ([E2B pricing](https://e2b.dev/pricing)) |
| Daytona | $0.0504/vCPU-h + $0.0162/GiB-h | ~$0.17 | Claims "sub 90ms" creation; isolation technology not stated ([Daytona pricing](https://www.daytona.io/pricing)) |
| Modal Sandboxes | ~$0.142/core-h + $0.024/GiB-h | ~$0.38 | 3x Modal Functions pricing ([Modal pricing](https://modal.com/pricing)) |
| Claude Managed Agents | $0.08/session-hour + tokens | n/a | **No ZDR or HIPAA eligibility** ([pricing](https://platform.claude.com/docs/en/about-claude/pricing); [overview](https://platform.claude.com/docs/en/managed-agents/overview)) |
| Customer's GitHub Actions | $0.006/min Linux 2-core | $0.36, billed to the customer | Code never leaves their CI ([GitHub pricing](https://docs.github.com/es/enterprise-server@3.15/billing/reference/actions-runner-pricing)) |

A five-minute verify run costs about **$0.014** on E2B. Sandbox spend is noise, but the configuration carries real risk. E2B's domain allowlists work **only for ports 80 and 443**, a denied TCP connection can *appear to succeed* from inside the sandbox, and there is no fixed egress IP list ([E2B internet access](https://docs.e2b.dev/network/internet-access); [E2B egress IPs](https://docs.e2b.dev/faq/egress-ip-ranges)). SHAPI should therefore turn off egress by default and route package installs through its own caching registry proxy, which also yields stable IPs and supply-chain logs. Clone with a short-lived, read-only installation token that expires before install scripts run, and **put no customer or provider secrets inside the sandbox**. CodeRabbit's January 2025 disclosure, in which Rubocop ran *outside* its sandbox, is the cautionary tale. Every tool that touches customer code, including linters and type checkers, runs inside the boundary ([CodeRabbit response](https://coderabbit.ai/blog/our-response-to-the-january-2025-kudelski-security-vulnerability-disclosure-action-and-continuous-improvement)). For security-sensitive buyers, a "bring your own runner" tier that pushes a branch and lets the customer's `pull_request` workflow run the generated test mirrors Dependabot's move onto Actions runners ([GitHub blog](https://github.blog/news-insights/product-news/dependabot-on-github-actions-and-self-hosted-runners-is-now-generally-available)). The caution here is to avoid `pull_request_target`, whose checkout-and-execute pattern is the classic compromise ([GitHub Docs](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/security/securely-using-pull_request_target)).

The repair loop should follow Agentless, not a free-roaming agent. Agentless localised narrowly, generated about 40 search/replace candidates, validated them with generated reproduction tests plus the repo's passing tests, and resolved **32% of SWE-bench Lite at about $0.70 per issue** ([Agentless](https://arxiv.org/html/2407.01489v2)). A better localiser alone raised its count from 96 to 115 of 300 resolved ([arXiv 2605.17965](https://arxiv.org/pdf/2605.17965)), and SHAPI's extractor *is* the localiser. The right Anthropic surface for a bounded task is the Messages API with a hand-written loop or the SDK tool runner. The Agent SDK fits only if SHAPI wants Claude Code's tools and hooks inside its own microVM, and third-party products built on it must use API keys and avoid "Claude Code" branding ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). Current prices make the economics easy. Sonnet 5.5 costs **$2/$10 per million input/output tokens**, cache reads cost 0.05x input, and Batch is 50% off ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). A four-turn, 60k-token repair with heavy caching comes to roughly **$0.09 on Sonnet 5.5 and $0.17 on Opus 5.5**, so five parallel candidates still cost under $0.50. The loop should expose narrow tools (`read_file`, `apply_search_replace_edit`, `run_contract_test`, `run_repo_tests`), mark test files read-only to the model, and pick the smallest diff that passes both gates. When nothing passes, it should open an issue or draft PR carrying the failing test and shape diff, never a speculative code PR.

Two dogfooding traps sit in SHAPI's own Claude fallback. Anthropic removed `temperature`, `top_p` and `top_k` in API version `2026-10-21`; they now return 400. `claude-sonnet-4-5-20250929` retires on **30 November 2026** ([Anthropic deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)). Public benchmarks also cannot validate the loop. OpenAI stopped reporting SWE-bench Verified in February 2026 over contamination ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). SHAPI's held-out eval should come from its own mined breakage-fix commits and track contract-pass rate, regression-pass rate, diff size, merge-without-edit rate, 30-day revert rate and cost per fix.

## Delivery and backend: a GitHub App with Renovate's manners on boring infrastructure

Moving off the user token is mandatory, not cosmetic. **Only GitHub Apps can create check runs** ([GitHub Checks](https://docs.github.com/en/rest/checks/runs)), and user tokens share one 5,000-request-per-hour budget across every app the user has authorised. Installation tokens get their own limit per installation: 5,000/hour base, growing to 12,500, and 15,000 on Enterprise Cloud ([GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). The binding constraint is the secondary limit on **content creation: about 80 per minute and 500 per hour**. Writes cost 5 points, and GitHub warns that continuing to send while rate-limited can get an integration banned ([GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Webhooks need equal discipline. GitHub drops any delivery not acknowledged with a 2xx within **10 seconds**, and "does not automatically redeliver failed deliveries", so a cron sweeper must list failed deliveries and redeliver them ([GitHub webhook docs](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)). `X-GitHub-Delivery` stays the same across redeliveries and serves as the dedupe key ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). The architecture follows from these limits. Ingress verifies the HMAC, inserts into Postgres under a unique constraint and returns 202. Workers run one job per repo with a token bucket per installation and at least a second between writes. PR work is keyed on (repo, advisory, branch), with deterministic branch names such as `shapi/<advisory-id>` so a rerun updates the existing PR instead of opening a duplicate. SHAPI must also check its code for 40-character token assumptions. Since **27 April 2026**, new installation tokens may use a longer stateless `ghs_` format ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). For the framework, Probot v14 is ESM-only and no longer ships an Express server ([JSR](https://jsr.io/@probot/bot@14.0.0/doc)). Plain `@octokit/app` with SHAPI's own queue is the lower-risk choice.

Noise control is the product. Renovate's defaults are a good starting point: **2 PRs per hour and 10 concurrent PRs per repo**, `rebaseWhen` set to auto, a `stop-updating` label that humans can apply, and `prCreation: status-success` so customers never see a red bot PR. Security PRs **bypass every limit and schedule** ([Renovate options](https://docs.renovatebot.com/configuration-options/)). SHAPI's version is a deadline carve-out: advisories already breaking, or with a near sunset date, skip the caps, and deprecation-only notices wait for a schedule or dashboard approval. Dependabot uses the same split, with 5 open version PRs, a fixed 10 for security fixes, and a 3-day cooldown ([Dependabot options](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference)). Renovate's single dashboard issue lets defaults stay conservative without hiding pending work ([Renovate dashboard](https://docs.renovatebot.com/key-concepts/dashboard/)). Its Merge Confidence badges, built from Mend PRs created since 2017, flag "undeclared breaking releases" ([Merge Confidence](https://docs.renovatebot.com/merge-confidence/)). That is the template for a SHAPI "Fix Confidence" score covering repos fixed, CI pass rate, merged-unedited rate and recipe-vs-LLM origin, with auto-merge allowed only at high confidence. The architecture lesson from Dependabot is that **dependabot-core is a stateless engine driven by JSON job definitions, and the coordinator is separate** ([Nesbitt](https://nesbitt.io/2026/01/02/how-dependabot-actually-works)). SHAPI's fix job should take (repo, base SHA, advisories, existing PR) and return file changes, a test, evidence and a decision, with close reasons stored and shown in the PR, which Dependabot does not do. Unlike Dependabot's polling, SHAPI should be event-driven: an advisory publish looks up affected installations in a reverse index, and a push triggers an incremental re-scan. Defining Renovate's `Platform`/`PlatformScm` seam now, with idempotent "ensure" semantics, makes GitLab and Bitbucket an implementation task later rather than a rewrite ([Renovate types.ts](https://raw.githubusercontent.com/renovatebot/renovate/main/lib/modules/platform/types.ts)). Moderne adds two more lessons for enterprise campaigns: one commit job per repo with bulk review, and progress measured by **re-running the recipe, not by counting merged PRs** ([Moderne docs](https://docs.moderne.io/user-documentation/moderne-platform/how-to-guides/track-commits)). Paid Marketplace listing requires 100 installations and verified-publisher status ([Marketplace requirements](https://docs.github.com/en/apps/github-marketplace/creating-apps-for-github-marketplace/requirements-for-listing-an-app)), so the sequence is a free listing, Stripe billing off-Marketplace, then a Marketplace plan.

At SHAPI's scale, about 100 APIs probed hourly comes to roughly 360k runs a month, which fits inside Hatchet's included runs. Shape history of about 4.4M rows a year is trivial for partitioned Postgres. Infrastructure before LLM spend should land around $100–250 a month. OAuth canary credentials have one sharp edge. QuickBooks refresh tokens change value roughly every 24 hours ([Intuit FAQ](https://developer.intuit.com/app/developer/qbo/docs/develop/authentication-and-authorization/faq)), and concurrent refreshes produce `invalid_grant` ([Nango](https://www.nango.dev/blog/quickbooks-oauth-refresh-token-invalid-grant)). Every refresh therefore runs as a single-flight job under a per-credential lock. On compliance, the posture to copy is CodeRabbit's: a sandbox provisioned per event and destroyed afterwards, "we do not store your code", no training on customer code, and SOC 2 Type II ([CodeRabbit FAQ](https://coderabbit.ai/FAQ)). Greptile's code caching paired with a self-hosted option ([Greptile security](https://greptile.com/security)) shows the enterprise alternative. Persisting only the call-site index, never source, keeps SHAPI on the CodeRabbit side of that line.

## The advisory database is the moat; competitors show what to avoid

Provider sources split into tiers, and **about half the top providers can be parsed without an LLM**. Stripe's changelog carries an explicit **"Breaking change?" column**, and every entry has a `.md` variant ([Stripe changelog](https://docs.stripe.com/changelog)). Shopify's quarterly `YYYY-MM` calendar, with at least 12 months of support, lets SHAPI *compute* sunset advisories before any changelog exists ([Shopify versioning](https://shopify.dev/docs/api/usage/versioning)). Meta publishes version expiry tables, with a Marketing API whose versions expire sooner than Graph's ([Meta versions](https://developers.facebook.com/docs/graph-api/changelog/versions)). OpenAI exposes `shutdown_date` on `GET /v1/models` ([OpenAI deprecations](https://developers.openai.com/api/docs/deprecations)). GitHub's changelog RSS tags retirements as "Retired" ([GitHub feed](https://github.blog/changelog/feed/)), and its OpenAPI descriptions are MIT-licensed for oasdiff spec diffs ([rest-api-description](https://webdrift.org.ntnu.no/cgit/index.cgi/rest-api-description/tree/README.md)). Free-form prose such as Slack's changelog needs LLM extraction ([Slack changelog](https://docs.slack.dev/changelog)). That extraction should be constrained. Classify only page *diffs*, require every date, endpoint and version to be quoted verbatim from the source, and reject unquoted fields, following Changes.Watch's rule that it "never invents these values from prose" ([Changes.Watch](https://www.changes.watch/developers/deprecations-catalog)). The research literature agrees that LLMs work best as "contract inference engines whose output can be verified by existing tools" ([arXiv 2605.24397](https://arxiv.org/pdf/2605.24397)). Ingesters also need redirect tracking and source-health alerts, because both OpenAI and Anthropic moved their docs domains behind 301s.

For the format, **OSV 1.9.2 (13 October 2026) already fits**. `id` and `modified` are required, `withdrawn` and `aliases` handle the lifecycle, and `affected[]` takes ECOSYSTEM ranges plus `ecosystem_specific`/`database_specific` extension points ([OSV schema](https://ossf.github.io/osv-schema/)). In SHAPI's mapping, the provider becomes the package, dated API versions become an ECOSYSTEM ordering, and the endpoint, fields and recipe go in the extensions. A second `affected[]` entry with SEMVER ranges covers each SDK, so lockfile scanners also match. OSV IDs must be semantically neutral, and severity is limited to CVSS types, so SHAPI's change class and dates must live in `database_specific`. GHSA supplies the governance model: a `github_reviewed` flag instead of separate folders, a staging branch for each community PR, and **CC-BY 4.0** licensing ([github/advisory-database](https://github.com/github/advisory-database)). Neither Harbyn (about 187 dated deadlines across 39 vendors, iCal and Markdown only ([Harbyn](https://harbyn.com/deadlines))) nor Changes.Watch declares a data license. An explicitly CC-BY-licensed, endpoint-granular database would be a real differentiator for tool builders. It would also serve the RFS's provider-led path, in which providers publish advisories in SHAPI format.

The competitor record points to four lessons, and the risk register follows from them.

Renovate's rise has a structural explanation: an open, stateless AGPL engine with a closed but self-hostable scheduler, spanning many SCMs ([Nesbitt](https://nesbitt.io/2026/01/02/how-dependabot-actually-works)). SHAPI's equivalent is an open advisory database and scanner with a hosted coordinator, and that openness doubles as distribution.

## Conclusion

The research shifts where SHAPI's engineering effort should go. The instinct is to perfect detection, but detection is the most commoditised layer. oasdiff, OTel and canaries are cheap, and indie rivals already alert for $10 a month. The hard, defensible problems sit downstream. One is a sensor that security teams approve, built on Akita's "infer client-side, strip values" precedent rather than on eBPF. Another is a sandbox that cannot leak, where a misconfigured egress filter is more dangerous than a missing language. The last is a fix pipeline whose evidence (failing-then-passing test, shape diff, cross-customer confidence) lets an engineer merge without re-deriving the change. Each verified merge improves the next fix's confidence score, so the dataset grows with adoption in the same way Renovate's Merge Confidence did, and no acquirer of producer-side tooling owns that consumer-side signal.

Three things remain uncertain and should be tested before they are assumed. No public benchmark exists for LLM classification of changelog entries, or for merge-without-edit rates on LLM-authored PRs, so SHAPI's first credible marketing asset may be publishing its own numbers from its mined-commit gold set. No primary source confirmed overhead figures for in-process body-shape hooks, so a benchmark should precede any "negligible overhead" claim. Provider ToS for automated probing and republishing derived change data has not been legally reviewed, and that review should come before the advisory database goes public. The practical order follows from the gaps. First, move to the GitHub App and a real microVM, which are prerequisites for any paying customer. Second, embed oasdiff and extend contract tests to SDK call sites. Third, scale the advisory database with deterministic adapters. Multi-language extraction comes last, because its value depends on fixes that already work.
